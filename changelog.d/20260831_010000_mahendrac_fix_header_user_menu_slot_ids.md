- [BugFix] Custom header user-menu (avatar toggle + Dashboard/Profile/Account/[Control Hub/Studio]/Sign out dropdown) wasn't rendering on `discussions`, `communications`, `ora-grading`, or `learning`. Those four MFEs render `LearningHeader`, not the plain `Header`/`DesktopHeader` that `account`/`profile`/`gradebook`/`learner-dashboard` use — `LearningHeader` exposes a *different* set of PluginSlot ids (`header_learning_user_menu.v1` / `header_learning_user_menu_toggle.v1`, not `header_desktop_user_menu*`). The previous version applied the desktop ids to every MFE uniformly, which silently no-oped on the four LearningHeader apps (the PluginSlot with that id never existed there, so nothing was hidden or inserted — the native header just kept showing). `HEADER_USER_MENU_SLOTS` now records the real, per-MFE (header component, dropdown-contents slot id, toggle slot id) verified against each MFE's actual locked `@edx/frontend-component-header` version on this project's `release/ulmo.1` pin. Also fixes: the user-menu *toggle* PluginSlot (the avatar/name button itself) didn't exist before `@edx/frontend-component-header` 6.6.0 — `profile` (6.4.2) and `ora-grading` (6.4.0) predate it, so only their dropdown contents can be overridden; `profile` additionally gets a `header_desktop.v1`/`header_mobile.v1` mergeProps fallback to at least show the full display name + photo on its native toggle, since the toggle-specific slot isn't available there. `ora-grading`'s toggle stays fully native — `LearningHeader` doesn't accept a username/avatar override prop, so there's no override point short of a source patch, which is out of scope for this method.
